# Publishing a new version

1. Bump the version in `Cargo.toml` (e.g., `0.1.2` → `0.1.3`)
2. Sync `Cargo.lock` with the new version
3. Check that lints and tests pass
4. Commit `Cargo.toml` and `Cargo.lock`
5. Create a git tag matching the version
6. Push the commit and the tag

```bash
cargo update --workspace

cargo clippy
cargo test
uv run maturin develop
uv run pytest

git add Cargo.toml Cargo.lock
git commit -m "bump version to x.x.x"
git tag x.x.x
git push origin main x.x.x
```

Notes:
- `cargo update --workspace` only updates this crate's entry in `Cargo.lock`; it does not upgrade dependencies.
- The published version comes from `Cargo.toml`, not from the tag. If you tag without bumping, CI builds every wheel and then fails to upload because that version already exists on PyPI.
- Push only the new tag. `git push --tags` pushes every local tag, and each tag push triggers a publish attempt.

The GitHub Actions CI workflow (`.github/workflows/CI.yml`) triggers on tag pushes and will:
- Build wheels for all platforms (Linux, macOS, Windows, musllinux)
- Install each wheel and run the Python tests against it
- Publish to PyPI automatically, but only if all builds and tests succeed

Clippy and the Rust tests run in a separate workflow (`.github/workflows/test.yml`) on pushes to `main` and on pull requests. They don't block publishing, so check that the commit you tag is green.

# Regenerating CI.yml

`CI.yml` is generated by maturin. Don't edit it by hand: change the `[tool.maturin.generate-ci.github]` settings in `pyproject.toml` and regenerate it:

```bash
uvx maturin generate-ci github -o .github/workflows/CI.yml
```

Things that maturin can't generate, like extra jobs, go in a separate workflow file such as `test.yml`.

When setting targets for a platform, list every platform. Platforms that are left out are dropped from the generated workflow.
